# ADR-001: Skill Taxonomy（5 维度分类）

**ID**: ADR-001
**日期**: 2026-05-20
**状态**: 已批准
**关联**: RF-001, ADR-006

---

## 上下文

在技能系统中，技能数量持续增长（当前 39 个）。需要一种分类方法来：

1. 决定新技能应该落在哪个类别
2. 帮助 Agent 在遇到问题时选择正确的技能
3. 为 AgenticDSL 的语言扩展提供设计依据

## 可选方案

### 方案 A：按技术栈分类（如 CMake 技能、C++ 技能、CUDA 技能）
- 优点：直观，与项目结构对应
- 缺点：无法区分"做什么"和"用什么做"，流程类技能无处安放

### 方案 B：按用途功能分类（如构建工具、调试工具、搜索工具）
- 优点：功能导向
- 缺点：粒度不均匀，无法覆盖流程/方法论类

### 方案 C：按抽象层分类（所选方案）
- 5 个维度，每个维度回答一个不同的问题

## 决策

选择 **方案 C**，分为 5 个轴：

| 轴 | 分类 | 核心问题 | 约束力 | 技术绑定 |
|----|------|---------|--------|---------|
| 轴1 | 流程/方法论 | 它强制你"先做 A 才能做 B"吗？ | 高 | 低 |
| 轴2 | 领域/工具 | 它告诉你"用什么工具/查什么文档"吗？ | 中 | 高 |
| 轴3 | 审查/质量 | 它说"交付前必须过这个检查"吗？ | 高 | 中 |
| 轴4 | UI/前端 | 它涉及 UI/UX/视觉呈现吗？ | 中 | 高 |
| 轴5 | 项目专用 | 它只在当前仓库有效吗？ | 高 | 高 |

## 分类判断流程

```
看到这个技能 → 问自己一个问题序列 → 归属：
  1. 只在本项目有效？        → 轴5-项目专用
  2. 涉及视觉/UI？           → 轴4-UI/前端
  3. 交付前必须过的检查？    → 轴3-审查/质量
  4. 告诉你用什么技术/工具？ → 轴2-领域/工具
  5. 否则 → 轴1-流程/方法论
```

## 跨轴技能处理

有些技能天然跨轴（如 `verification-before-completion` 既是流程也是审查）。处理方式：

```
确定主轴（Primary Axis）：
  - 该技能的核心目的是什么？
  - 如果拿掉它，哪个轴会受影响最严重？

例：
  verification-before-completion → 主轴=审查（本质是质量门禁）
  receiving-code-review → 主轴=审查（本质是验证反馈正确性）
  writing-skills → 主轴=流程（本质是创建技能的工作流步骤）  
  git-master → 主轴=领域（本质是 Git 操作工具集）
```

## 影响

- 正面：新技能定位清晰，Agent 选择技能的路径可预测
- 正面：为 AgenticDSL 的 5 个扩展方向（ideal_dsl/03~05）提供设计依据
- 负面：少数技能需要跨轴判断，增加分类成本

## 验证

- 全量 39 个去重技能成功映射到 5 个维度，无遗漏
- 跨轴 6 个技能的主轴归属一致
